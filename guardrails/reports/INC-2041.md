## Root cause
`shopfront/promotions.py:16` — `_parse_expiry` truncated the ISO-8601 expiry string to 19 characters (`[:19]`), silently discarding the UTC offset (`-06:00`). The resulting naive datetime represented merchant local time, but `is_active` compared it against `datetime.utcnow()` (also naive but already UTC). When the UTC clock hit 18:00 on 2025-11-28 the UTC value numerically exceeded the naked `23:59` local string, marking BF30 expired six hours before the intended midnight Central deadline.

## Bug class
Timezone offset silently discarded when parsing ISO-8601 strings, causing naive-vs-naive datetime comparisons that are wrong by the full UTC offset.

## Regression test
`tests/test_inc_2041_promo_timezone.py::test_promo_active_at_18_utc_on_black_friday`. Failed before the fix with:
```
TypeError: can't compare offset-naive and offset-aware datetimes
```

## Fix
Two minimal changes to `shopfront/promotions.py`:
1. `_parse_expiry`: replaced `datetime.strptime(expires_at[:19], "%Y-%m-%dT%H:%M:%S")` with `datetime.fromisoformat(expires_at)` — preserves the UTC offset, returning a timezone-aware datetime.
2. `is_active`: replaced `datetime.utcnow()` with `datetime.now(timezone.utc)` — returns a timezone-aware UTC datetime so the comparison is aware-vs-aware and correct.

These are the smallest changes that make the comparisons timezone-correct without altering any other logic.

## Guardrail
